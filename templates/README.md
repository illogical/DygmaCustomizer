# Layer templates

Each JSON template names a reusable group of actions and proposed **L1 reference positions**. A group can fill a layer or add only a few keys to an existing layer. A profile supplies one computer's OS, installed apps, and shortcut overrides. `scripts/resolve_template.py` prints a cheat sheet; `scripts/apply_template.py` previews collisions and can write a distinct virtual Bazecor JSON for encodings already verified in this project. Neither command changes a connected keyboard.

```sh
python3 scripts/resolve_template.py templates/vscode.json --os macos
python3 scripts/resolve_template.py templates/vscode.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/app-launcher.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/omarchy.json --profile profiles/omarchy.example.json
python3 scripts/resolve_template.py templates/tmux.json --profile profiles/omarchy.example.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/blender-view.json --os macos --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/macos-navigation.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/apply_template.py preview examples/VirtualDefy.json templates/macos-navigation.json --target 4 --profile profiles/macbook-pro-m5.local.json
```

The VS Code template gives explicit Mac, Windows, and Linux shortcuts for the same named actions. It deliberately does not perform a global `Cmd` ↔ `Ctrl` replacement: navigation and other defaults differ by OS. A profile may override a shortcut by `template-id.action-id`. An action without an OS shortcut or profile override is omitted and reported, not guessed. `requires_app` and `requires_environment` filter actions for a particular machine. An `available_apps` list is an assertion supplied by the user; it is not an automatic inventory. A missing profile app is reported as skipped.

`profiles/*.local.json` and optional `PERSONALIZATION.md` notes are ignored by Git because they describe one user's computers. The tracked `*.example.json` profiles and initialization manifests show the reusable structure. Put action definitions and color purposes in templates, machine-specific shortcuts in a profile, and layer destinations and palette-slot purposes in a PC manifest. The local Mac profile records the 13 application hotkeys visible in the supplied Raycast screenshot. Its Hyper modifier expands to Ctrl+Alt+Cmd+Shift based on this Mac's Raycast setting, but test the resulting shortcut in Raycast before encoding it in Bazecor.

The Markdown output can be saved as a cheat sheet when a design is ready: `python3 scripts/resolve_template.py templates/vscode.json --os macos --source-json examples/VirtualDefy.json > vscode-macos-cheatsheet.md`. The `--format json` output preserves action IDs and resolved physical positions for a future Bazecor compiler. Neither output changes a keyboard.

Keep **L1 labels in conversation**, because “the L1 `F` position on the Blender layer” is easy to say. Store `position_id` as the durable location in a Defy template, for example `defy:left:r3:c5` (one-based physical row and column, viewed from that half). The thumb keys use the same IDs: left “Super 1” is `defy:left:r5:c1`, right “Macro 1” is `defy:right:r5:c4`, Battery Level is `defy:right:r5:c2`, and Bluetooth Pairing is `defy:right:r5:c1` in the preserved source. Their proposed L4 destinations remain `defy:right:r5:c7` and `defy:right:r5:c8`. `position_l1` is a human mnemonic/hint. The resolver reads `device.keyboard` from the chosen source to turn `position_id` into its current keymap index and reports when the L1 label there has changed. Key indices are derived output, not identity. Check geometry compatibility when using another model or a substantially different Defy export. Older templates without `position_id` still use a unique L1 label and reject ambiguity.

## Color design and coordination

Plan colors at two levels. Give each layer a recognizable identity color or slot so you can tell at a glance which layer is active. Within a layer, assign semantic purpose colors to key groups where that adds useful meaning. When two layers contain actions with a genuinely shared purpose, consider using the same purpose color for those keys on that computer; this should be an intentional, occasional reuse, not a requirement. Keep those shared meanings in the templates and their slot mappings in PC manifests. A binding's `color_category` names its purpose. An optional `color_slots` map connects slot IDs to purpose names, for example `"color_slots": {"5": "navigation", "9": "destructive"}`. Put machine-specific mappings on each entry of a PC initialization manifest; they override a template's optional map. The tool checks that each referenced slot exists, but does not compare RGB(W) values because a slot can have different colors on different computers. Suggested purpose names include `navigation`, `search`, `transform`, `mesh`, `create`, `view`, `workspace`, `session`, `mode`, and `destructive`. Record the chosen activation and return positions in the navigation templates and PC manifest; verify the LED mapping before assigning thumb colors.

Add a slot-to-purpose mapping to a PC manifest entry or its template fallback to set per-layer LED references. The mapping never edits the global palette. Use `scripts/defy.py set-palette` separately to change a palette value, noting that all LEDs referencing that slot change on every layer. Color application covers the left half and first three right rows in this snapshot; the third right row is inferred from contiguous row geometry anchored by the L8 color fixture and needs a Bazecor visual check. Lower right rows remain unmapped.

`apply_template.py preview INPUT TEMPLATE --target N --profile PROFILE` is read-only. By default, preview and apply include key assignments and mapped colors. Use `--keys-only` to preserve LEDs, or `--colors-only` to preserve key assignments; color-only mode can apply a binding even when it has no shortcut. Apply also accepts optional `--output`; its default output is `INPUT-LN-TEMPLATE.json`. Occupied assignments stop an apply by default. `--fill-empty` skips occupied keys and their LEDs, `--override` replaces only named positions, and `--replace-layer --baseline CLEAN.json` clears the selected key assignments to transparent and restores baseline lighting for the selected aspect before applying. Apply refuses unsupported requested changes and skipped actions (`--allow-skipped` opts into a partial single-template result). The output preserves the source JSON and all commands outside the selected keymap and colormap edits.

For one PC, list template and displayed-layer pairs in `profiles/*.init.local.json`. Multiple entries may target one layer; they are composed in manifest order. Strict mode blocks different actions at the same position, `--override` makes later entries win, and `--replace-layer` resets a target only once before applying all its entries. `--only-layer N` selects every entry for that displayed layer. A manifest may map logical navigation roles to that PC's displayed layer numbers with `layer_targets` (for example, `primary`, `secondary`, `tertiary`, `rare`, and `base`). This lets the same navigation template target different layer arrangements on Mac and Omarchy.

The Mac manifest applies `layer-navigation.json` and `device-controls-clear.json` to L1; `app-launcher.json` and `device-controls.json` to L4; and `layer-return.json` to L5. L7 is unused. Battery and Bluetooth controls move from L1 right-thumb c2/c1 to L4 c7/c8, and their original L1 positions become transparent. `app-launcher.json` keeps the One Shot trigger position transparent on L4. Use `--override` for the selected L1 trigger and cleared positions. The saved L8 fixture and current Bazecor tables support One Shot Layer L4, Move to L1, and the profile's Hyper, VS Code, and macOS navigation chords. The Superkey gestures remain unresolved. In deferred mode, a combined output requires a verified LED mapping so the unresolved key can be red; configured keys with unmapped LEDs retain their original lighting.

Template schema v1 keeps portable intent: `id`, `name`, `platforms`, optional `environment`, `source`, `activation`, `color_slots` (slot ID strings mapped to purpose names), and `bindings`. A binding has stable `id`, human `name`, `position_id`, `position_l1`, `color_category`, optional `requires_app`, OS `shortcuts`, or a declarative `bazecor_action`. Action descriptors name One Shot Layer, Layer Lock, Move to Layer, Layer Shift, Superkey gestures, transparent positions, and device commands; the resolver maps layer roles using `layer_targets`. The applier encodes Move to Layer from the saved L5/L7 examples and Bazecor's matching table, while Layer Lock remains a distinct behavior. Other descriptors without enough evidence are reported as unsupported and prevent output. A shortcut is one chord (`Ctrl+B`) or an ordered array (`["Ctrl+B", "V"]`) with a release between steps. Profiles carry `os`, optional `environment` and `version`, `available_apps`, `hyper_modifiers`, and `shortcut_overrides`. Keep action IDs stable so future cheat sheets and migration tools can refer to them.

The tmux template proposes H/J/K/L for pane focus, V and D for splits, C for a new window, N/P for switching, Z for zoom, X for closing, and Q for detaching. Its default split bindings assume a US-style `Shift+5` (`%`) and `Shift+Quote` (`"`). Check terminal key transmission and any custom prefix before applying. A held Layer Shift is proposed for repeated pane navigation. [tmux Getting Started](https://github.com/tmux/tmux/wiki/Getting-Started).

The two Blender templates are a starting design based on the documented **Blender default keymap**: modeling uses familiar G/R/S transforms and nearby mesh operations, while viewport navigation gives the Defy direct Numpad view actions. Blender also ships an [Industry Compatible keymap](https://docs.blender.org/manual/en/latest/interface/keymap/industry_compatible.html); its different commands require a separate template if selected. The modeling template is context-sensitive in Blender's 3D Viewport and Edit Mode. Many of its single-letter commands already work on L1; use it as an annotated candidate and keep only actions that earn a dedicated layer position in actual use. The view template adds more distinct value on a compact keyboard: it requires actual Numpad keycodes, not number-row keys. A held Layer Shift is proposed for repeated view/orbit actions. [Blender keymap guide](https://docs.blender.org/manual/en/latest/interface/keymap/index.html), [viewport navigation](https://docs.blender.org/manual/en/3.5/editors/3dview/navigate/navigation.html).

The macOS navigation template groups desktop switching on H/L, app switching on J/K, current-app windows on U/I, and screenshot on S. [Apple documents](https://support.apple.com/en-us/102650) Cmd+Tab, Cmd+Grave, and Shift+Cmd+4; [Control+Left/Right switches Spaces](https://support.apple.com/en-hk/guide/mac-help/mh14112/mac) by default. This user's Mac profile overrides desktop switching to Ctrl+Cmd+Arrow and screenshot to Shift+Ctrl+C. These positions are proposals and may conflict with other templates on a shared layer.

`gaming-fps.json` and `gaming-rpg.json` propose separate Windows gaming layers. Both keep WASD and nearby actions on the left, place 1–6 across the left top row (the L1 `-` position emits `6`), and reserve right I/J/K/L for arrows plus the right `Space` thumb position for Enter. The RPG version brings inventory (`I`) to the L1 `T` position and map (`M`) to the L1 `G` position. Left `Super 1` and the adjacent thumb position propose Ctrl and Alt; confirm their physical labels and feel in Bazecor. `identity_color` records an amber FPS or violet RPG layer identity proposal; it does not allocate a palette slot or change lighting. Shared `movement`, `action`, `quick-slot`, `modifier`, and `menu` categories describe purpose. Check game-specific bindings, especially I/M and numbers, before use. Activation and return behavior remain to be chosen. The current applier does not encode Esc, Shift, Ctrl, Alt, or Enter without current Bazecor fixtures, and right-side LED mapping is incomplete; resolve and preview first, then use a Windows-specific virtual export for any eventual apply.

The [VS Code default keybindings](https://code.visualstudio.com/docs/reference/default-keybindings) and [Omarchy hotkeys manual](https://github.com/omacom/omarchy/blob/quattro/manual/07-hotkeys.md) were read on 2026-10-03. The Omarchy sample is based on the current `quattro` manual while [v4.0.4 was the latest release](https://github.com/omacom/omarchy/releases) at that time; compare it with `Super+K` and your installed Omarchy version before applying it. Its source may evolve. App launch shortcuts also depend on the host app and user settings.
