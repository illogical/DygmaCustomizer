# Layer templates

Each JSON template names a reusable group of actions and proposed **L1 reference positions**. A group can fill a layer or add only a few keys to an existing layer. A profile supplies one computer's OS, installed apps, and shortcut overrides. `scripts/resolve_template.py` prints a cheat sheet; `scripts/apply_template.py` previews collisions and can write a distinct virtual Bazecor JSON for encodings already verified in this project. Neither command changes a connected keyboard.

```sh
python3 scripts/resolve_template.py templates/vscode.json --os macos
python3 scripts/resolve_template.py templates/vscode.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/app-launcher.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/omarchy.json --profile profiles/omarchy.example.json
python3 scripts/resolve_template.py templates/herdr.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/tmux.json --profile profiles/omarchy.example.json --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/blender-view.json --os macos --source-json examples/VirtualDefy.json
python3 scripts/resolve_template.py templates/macos-navigation.json --profile profiles/macbook-pro-m5.local.json --source-json examples/VirtualDefy.json
python3 scripts/apply_template.py preview examples/VirtualDefy.json templates/macos-navigation.json --target 4 --profile profiles/macbook-pro-m5.local.json
```

The VS Code template gives explicit Mac, Windows, and Linux shortcuts for the same named actions. It deliberately does not perform a global `Cmd` ↔ `Ctrl` replacement: navigation and other defaults differ by OS. A profile may override a shortcut by `template-id.action-id`. An action without an OS shortcut or profile override is omitted and reported, not guessed. `requires_app` and `requires_environment` filter actions for a particular machine. An `available_apps` list is an assertion supplied by the user; it is not an automatic inventory. A missing profile app is reported as skipped.

`profiles/*.local.json` and `PERSONALIZATION.md` are ignored by Git because they describe one user's computers. The tracked `*.example.json` profiles show the structure. The Mac profile here records the 13 application hotkeys visible in the supplied Raycast screenshot. Its Hyper modifier expands to Ctrl+Alt+Cmd+Shift based on this Mac's Raycast setting, but test the resulting shortcut in Raycast before encoding it in Bazecor.

The Markdown output can be saved as a cheat sheet when a design is ready: `python3 scripts/resolve_template.py templates/vscode.json --os macos --source-json examples/VirtualDefy.json > vscode-macos-cheatsheet.md`. The `--format json` output preserves action IDs and resolved physical positions for a future Bazecor compiler. Neither output changes a keyboard.

Keep **L1 labels in conversation**, because “the L1 `F` position on the Blender layer” is easy to say. Store `position_id` as the durable location in a Defy template, for example `defy:left:r3:c5` (one-based physical row and column, viewed from that half). `position_l1` is a human mnemonic/hint. The resolver reads `device.keyboard` from the chosen source to turn `position_id` into its current keymap index and reports when the L1 label there has changed. Key indices are derived output, not identity. Check geometry compatibility when using another model or a substantially different Defy export. Older templates without `position_id` still use a unique L1 label and reject ambiguity.

## Color design and coordination

Plan colors at two levels. Give each layer a recognizable identity color or slot so you can tell at a glance which layer is active. Within a layer, assign semantic purpose colors to key groups where that adds useful meaning. When two layers contain actions with a genuinely shared purpose, consider using the same purpose color for those keys on that computer; this should be an intentional, occasional reuse, not a requirement. Keep those shared meanings consistent in their templates and in `PERSONALIZATION.md` when present. A binding's `color_category` names its purpose. An optional `color_slots` map connects slot IDs to purpose names, for example `"color_slots": {"5": "navigation", "9": "destructive"}`. Put machine-specific mappings on each entry of a PC initialization manifest; they override a template's optional map. The tool checks that each referenced slot exists, but does not compare RGB(W) values because a slot can have different colors on different computers. Suggested purpose names include `navigation`, `search`, `transform`, `mesh`, `create`, `view`, `workspace`, `session`, `mode`, and `destructive`. Distinguish destructive actions from creation actions at a glance. `activation` is a proposal; its thumb position remains open until a user selects it.

Add a slot-to-purpose mapping to a PC manifest entry or its template fallback to set per-layer LED references. The mapping never edits the global palette. Use `scripts/defy.py set-palette` separately to change a palette value, noting that all LEDs referencing that slot change on every layer. Color application currently covers only physical keys with a verified key-to-LED map (left half and right top row in this snapshot).

`apply_template.py preview INPUT TEMPLATE --target N --profile PROFILE` is read-only. By default, preview and apply include key assignments and mapped colors. Use `--keys-only` to preserve LEDs, or `--colors-only` to preserve key assignments; color-only mode can apply a binding even when it has no shortcut. Apply also accepts optional `--output`; its default output is `INPUT-LN-TEMPLATE.json`. Occupied assignments stop an apply by default. `--fill-empty` skips occupied keys and their LEDs, `--override` replaces only named positions, and `--replace-layer --baseline CLEAN.json` clears the selected key assignments to transparent and restores baseline lighting for the selected aspect before applying. Apply refuses unsupported requested changes and skipped actions (`--allow-skipped` opts into a partial single-template result). The output preserves the source JSON and all commands outside the selected keymap and colormap edits.

For one PC, list separate template and displayed layer pairs in `profiles/*.init.local.json`. `scripts/apply_template_set.py preview INPUT MANIFEST` reports all proposed layers; `apply` writes one output only if all are ready. `--only-layer N` selects one manifest entry when refining or repurposing a layer. The tracked `profiles/macos-init.example.json` and this user's local Mac manifest assign L4–L7 to app launcher, VS Code, macOS navigation, and Herdr. The tracked `profiles/omarchy-init.example.json` assigns L4 Omarchy, L5 Herdr, and L6 tmux using the Omarchy example profile. Preview this against a fresh Defy virtual JSON, then confirm Omarchy and terminal shortcuts on that PC. Current previews are blocked by unverified Bazecor encodings, missing color mappings, and unverified right-side LED geometry; the Mac preview also lacks Finder's shortcut.

Template schema v1 keeps portable intent: `id`, `name`, `platforms`, optional `environment`, `source`, `activation`, `color_slots` (slot ID strings mapped to purpose names), and `bindings`. A binding has stable `id`, human `name`, `position_id`, `position_l1`, `color_category`, optional `requires_app`, and optional `shortcuts` keyed by OS. A shortcut is one chord (`Ctrl+B`) or an ordered array (`["Ctrl+B", "V"]`) with a release between steps. Prefix-driven Herdr/tmux actions use arrays; a future Bazecor encoder will have to verify and encode them as macros or another suitable feature. Profiles carry `os`, optional `environment` and `version`, `available_apps`, `hyper_modifiers`, and `shortcut_overrides`. `Hyper` expands to the profile's actual modifiers; if unset, resolution fails for that action. Keep action IDs stable so future cheat sheets and migration tools can refer to them.

The Herdr and tmux templates deliberately use the same **physical positions** for comparable tasks: H/J/K/L move among panes; V and D split; C creates a tab/window; N/P switch; Z zooms; X closes a pane; Q detaches. Their emitted keys differ, and tmux's default split bindings assume a US-style `Shift+5` (`%`) and `Shift+Quote` (`"`). Check terminal key transmission and any custom prefix before applying. A held Layer Shift is proposed because pane navigation may be repeated; One Shot Layer can be evaluated later. Herdr also documents user-defined direct `Ctrl+Alt` bindings; if chosen on a particular host, a profile override could use one chord per action and avoid keyboard macros. Confirm that the terminal and OS pass those chords through. [Herdr keyboard guide](https://herdr.dev/docs/keyboard/), [tmux Getting Started](https://github.com/tmux/tmux/wiki/Getting-Started).

The two Blender templates are a starting design based on the documented **Blender default keymap**: modeling uses familiar G/R/S transforms and nearby mesh operations, while viewport navigation gives the Defy direct Numpad view actions. Blender also ships an [Industry Compatible keymap](https://docs.blender.org/manual/en/latest/interface/keymap/industry_compatible.html); its different commands require a separate template if selected. The modeling template is context-sensitive in Blender's 3D Viewport and Edit Mode. Many of its single-letter commands already work on L1; use it as an annotated candidate and keep only actions that earn a dedicated layer position in actual use. The view template adds more distinct value on a compact keyboard: it requires actual Numpad keycodes, not number-row keys. A held Layer Shift is proposed for repeated view/orbit actions. [Blender keymap guide](https://docs.blender.org/manual/en/latest/interface/keymap/index.html), [viewport navigation](https://docs.blender.org/manual/en/3.5/editors/3dview/navigate/navigation.html).

The macOS navigation template groups desktop switching on H/L, app switching on J/K, current-app windows on U/I, Finder on F, and screenshot on S. [Apple documents](https://support.apple.com/en-us/102650) Cmd+Tab, Cmd+Grave, and Shift+Cmd+4; [Control+Left/Right switches Spaces](https://support.apple.com/en-hk/guide/mac-help/mh14112/mac) by default. This user's Mac profile overrides desktop switching to Ctrl+Cmd+Arrow and screenshot to Shift+Ctrl+C. A global Finder launcher has no confirmed keybinding yet, so that action is skipped until a profile supplies one. These positions are proposals and may conflict with other templates on a shared layer.

The [VS Code default keybindings](https://code.visualstudio.com/docs/reference/default-keybindings) and [Omarchy hotkeys manual](https://github.com/omacom/omarchy/blob/quattro/manual/07-hotkeys.md) were read on 2026-10-03. The Omarchy sample is based on the current `quattro` manual while [v4.0.4 was the latest release](https://github.com/omacom/omarchy/releases) at that time; compare it with `Super+K` and your installed Omarchy version before applying it. Its source may evolve. App launch shortcuts also depend on the host app and user settings.
