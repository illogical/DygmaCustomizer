# Project instructions

- This project builds reusable Dygma keyboard customizations, starting with the Defy. Use virtual Bazecor JSON while no physical keyboard is connected; later confirm compatibility and apply changes through Bazecor to a connected keyboard. A virtual file alone does not change the keyboard.
- Use L1 as the default vocabulary for physical key positions: “the `1` key on L4” means the position occupied by `1` on L1, with L4 as the destination. If an L1 label occurs more than once or is unclear, resolve the position with the user before editing.
- Keep each input JSON intact. Write a distinct output file, then verify the intended key and color changes and the absence of unrelated changes. Do not overwrite a virtual file that Bazecor may currently be using unless explicitly requested.
- For Defy layout or lighting changes, follow [the project skill](.agents/skills/edit-dygma-defy/SKILL.md). Use [the customization guide](CUSTOMIZATION_GUIDE.md) to translate natural language into shortcuts, macros, Superkeys, layer behavior, and a verification plan. The JSON snapshots are in `examples/`.
- Run `python3 -m unittest discover -s scripts -p 'test_*.py' -v` after changing a project script. Update `README.md` when the supported workflow or loading instructions change.
- Record future intentions mentioned in passing as checkboxes in `docs/FUTURE_TASKS.md`, keeping the current task in focus. Mark an item complete only when its intended work is verified.
- Read `PERSONALIZATION.md` when it exists for this user's goals, but do not require or maintain it as a parallel template specification. Keep reusable actions and purpose categories in `templates/`, computer-specific shortcuts in profiles, and layer assignments and palette-slot meanings in PC manifests. Treat any personal notes as proposals until verified in a source JSON and Bazecor.
- Use Dygma's names: Layer Shift (active while held), Layer Lock (toggle), and One Shot Layer (next keystroke; hold/double-tap behavior depends on the assigned key). Say which behavior is requested before encoding it. Keep a way back to the base layer.
- Prefer `scripts/defy.py` for supported copies and palette/LED edits. Inspect slot usage first and record semantic color categories in templates and PC manifests; palette slot IDs alone do not convey purpose.
- Before editing a macro, Superkey, layer trigger, or another unsupported serialized command, build a minimal example in the current Bazecor UI and compare its saved JSON against a preserved source. Track references and timing settings. Do not infer an encoding solely from a generic or older API example.
- For named, portable layer designs, read `templates/README.md`. Resolve one template with a machine profile and `scripts/resolve_template.py` before encoding it in Bazecor. Treat templates and previews as proposed behavior; verify L1 positions against the chosen JSON, OS/app shortcuts against the host, and colors against the target palette.
- Keep L1 labels as the default user-facing physical-position vocabulary. In a Defy template, store a stable `position_id` of side/row/column plus the L1 label as a mnemonic. Resolve the current keymap index from `device.keyboard` in the selected source; flag label changes, and do not identify a physical key solely by a mutable L1 assignment.
- For “where is this key?” or “does this computer have this action?” use the read-only `scripts/query_layout.py` workflow in the project skill. Ground current assignments in an identified configuration JSON, cross-check purpose names against the PC manifest/profile, and label unmatched manifest entries as proposals. Do not select a current file by modification time.
- Treat templates as partial sets of named actions that can augment an existing layer. Preview before applying. Occupied keys stop an apply by default; `--fill-empty` skips occupied keys and their colors, `--override` replaces named positions, and `--replace-layer --baseline CLEAN.json` clears the target layer's keys to transparent and restores baseline lighting. Both keys and mapped colors apply by default; `--keys-only` and `--colors-only` select one. Use `scripts/apply_template_set.py` with a PC manifest to compose separate layers into one output; blocked actions prevent any output. A manifest entry may override a template's slot-to-purpose mapping for that PC. Do not require or infer RGB(W) values. Give each layer a recognizable identity color, and selectively reuse purpose colors across layers for action groups with a genuinely shared purpose. Never guess macro, Superkey, layer-trigger, or unverified modifier-combo keycodes.
